# Hostile cold audit: FT2_U5V1 (Track 1)

**Verdict: GAP in the submitted trusted verifier and proof text.** I did not falsify the enclosure for the two specifically named and hashed gold1 snapshots. Their replay was byte-for-byte identical to `certificate_gold1.json`; independent exact checks found no gold1 drift or comparability violation. The accepted-input verifier is nevertheless unsound: the wrapper can turn an upper bound into a lower bound, and the C++ verifier can silently understate a seam cap. The submitted proof also omits the actual double-tail argument and the integrability justification. Line references are to the submitted files, not repaired versions.

## Breaking findings and repairs

1. **Wrong one-sided theorem accepted as a lower bound** (`cert_check.py:548–560`). Replay `python3 -B cert_check.py --verify-bin [local path] --lower tiny_hi.bin --upper tiny_hi.bin --skip-trees`: succeeds and reports `[0.566848116168, 0.566848116168]`, width `0.0000`, `certifies_mu_gt_0_5657=true`, both modes `1`. There was no lower certificate. The same bug does not affect the actual gold1 assignment (`2,1`). **Repair:** explicitly require lower mode 2 and upper mode 1 and reject an inverted exact interval before printing any theorem; add a duplicate-upper and swapped-side test.
2. **Unchecked seam narrowing produces a false component certificate** (`quintet_format.hpp:34–37,68–99`; `verify_quintet.cpp:356–365,394–399`). On an anonymous in-memory copy of tiny lower, set only `f_p0` at byte offset `56` to `INT64_MIN`. Fresh release verifier exits 0. Checking all `c=0..119` of the seam with `Fraction` gives a maximum ceiling of **1097581622278273633202** ticks; C++ prints **8608771454101275355** for `f_tab`. The signed 128-bit expression is large but representable; narrowing is the failure. This mutation establishes a false C++ certificate component, not an end-to-end false interval (the analytic/comparability check may catch it). **Repair:** bound analytic coefficients and check each wide-to-narrow conversion, or keep and serialize wide exact caps. Regression-test the one-field mutation. Actual gold1 coefficients have magnitude less than `2^42`.
3. **Signed overflow in the validator** (`quintet_format.hpp:94–95`). An in-memory tiny copy with `knot_num[1] = 630 + 2^60` (byte offset `312`) triggers UBSan: `quintet_format.hpp:94:23: runtime error: signed integer overflow: 1152921504606847606 * 16 cannot be represented in type 'long int'`. Release mode happens to reject this input later at code 28; reaching that check after UB is not a valid validation argument. **Repair:** range-check every active knot numerator against `[0,Q_K]` before either product; also enforce `K3e<d3e`, `K4e<d4e`, `K5e<d5e` if the header is to certify the domain specified at `PROOF.md:29` (the extra phantom classes are conservative for physical instances).
4. **General layout and aggregation bounds do not follow from the accepted header** (`quintet_format.hpp:76–92,271–285,307–376,378–417`; `verify_quintet.cpp:974,1088–1194`). Equal 256 cutoffs and caps 255 are permitted for all endpoint and internal levels, with compatible budgets. This gives `N=32896`, `N^3=35598301659136`, and `C(N+2,3)=5933591360896`; three-dimensional flattened indices and `int` IDs/counts lack adequate range. Even `size_t` totals can overflow (e.g. the S4 payload size alone at maximal dimensions); layout construction attempts enormous allocations before inspecting actual file size. A bare degree-255 S4 host allows `C(255,4)=172061505` terms, whose allowed magnitude from this family alone can be `3026938007042213806080` ticks. Thus the 128-bit `hcap/lo_shifted/hi_w` to `int64_t` casts cannot be justified by the header and payload bounds. **Repair:** compute validated dimensions and totals with checked wide arithmetic *before* allocation; cap resource use and enforce representability for every dense index, ordered block ID/count and accumulated result. Use `size_t` consistently for dense indexes and checked range conversions or wide output for aggregation. Actual tiny/gold1 dimensions are small enough; their supported host caps and payload magnitudes make these conversions safe.
5. **Mutation and parsing inputs are insufficiently guarded** (`verify_quintet.cpp:168–224,244–264`; `cert_check.py:510–534`). Mutations run before payload magnitude validation, so `+=` or `-=1` can overflow on malformed values. When valid `d3m==d2`, `--perturb knots` reads an unpopulated exact index `-1` and derives an invalid payload index. `atoll`/`atoi` are not strict overflow-safe parsers, incomplete or nonpositive override values can be silently ignored, and thread counts are unchecked. `fseek/ftell` results are unchecked and the native binary layout assumes little-endian host, while Python specifies little-endian. `run_mutations` comments say exit 2 is required for structural rejection, but it only requires failure (and may access absent fields on a comparability failure). **Repair:** apply mutations only after base validation and range-check mutation targets/results; use strict numeric parsers; check exact I/O and endianness; assert expected diagnostic and exit for structural tests. Bind all stages to the same immutable snapshot rather than trusting separate pathname reads if accepting files that could change during verification.
6. **Build requirement fails** (`quintet_format.hpp:55–66`, `verify_quintet.cpp:27` onward). The requested GCC build succeeds with **284 `-Wpedantic` warnings**, all GNU `__int128` extension warnings; no other warning category was emitted. The math has no floating-point operations. **Repair:** isolate the deliberate extension, e.g. `__extension__ typedef __int128 Wide;`, and use that alias consistently (or use a rigorously bounded portable wide-integer implementation).
