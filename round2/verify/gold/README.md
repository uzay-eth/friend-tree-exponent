# Clean Gold certificate builds

Run from the repository root on x86-64 Linux with GCC, GNU `time` and GNU coreutils:

```sh
bash round2/verify/gold/rebuild.sh "$PWD/gold-rebuild"
```

The output directory must not already exist. Allow 16 GiB of free disk for all four snapshots (15,866,847,568 bytes total) and at least 10 GiB of available RAM for one builder; the builds run sequentially. Pass `gold1` or `gold2` as the optional second argument to build one pair. The script records compiler and CPU information, logs, elapsed time, maximum RSS and SHA-256. It attempts every requested build and exits nonzero if any build fails or any digest differs.

See [RESULTS.md](RESULTS.md) for the measured commands and outcomes.

`inputs.sha256` pins the builder and its sole project header to source commit `edd297185538b5ec399c04cb7fc80ebe2c07310a`. The builder takes only the preset, the side and the output filename. It computes its own starting data using `mt19937_64` seed `20261124`: 30 runs of size 180,000 for Gold1 and 32 runs of size 200,000 for Gold2. Both use the dimensions, 40 knot steps and iteration settings embedded in that revision. No previously computed weights or snapshots are inputs. `expected.sha256` holds the four historical snapshot digests from the two checked-in receipts.

To confirm the **committed** release sources match the pins, from the repository root:

```sh
set -eo pipefail
q=round2/proofs/neon2/quintet-cert
for f in build_quintet.cpp quintet_format.hpp; do
    git show "HEAD:$q/$f" | sha256sum | awk -v f="$f" '{print $1 "  " f}'
done | diff - round2/verify/gold/inputs.sha256
```

## Recorded environment

- AMD Ryzen 7 5800X, 8 physical cores / 16 logical CPUs, x86-64 little endian, CPU affinity `0–15`.
- Linux `6.8.0-151-generic`; GCC/G++ Ubuntu `13.3.0-6ubuntu2~24.04.1`, target `x86_64-linux-gnu`; glibc `2.39-0ubuntu8.12`; libgomp and libstdc++ `14.2.0-4ubuntu2~24.04.1`; GNU `time` package `1.9-0.2build1`.
- Compiler flags: `-std=c++17 -O3 -fopenmp -Wall -Wextra -Werror -pedantic`. No native architecture or fast-math flags.
- Runtime: `LC_ALL=C OMP_WAIT_POLICY=PASSIVE OMP_DYNAMIC=FALSE OMP_NUM_THREADS=10 OMP_THREAD_LIMIT=10 OMP_PROC_BIND=FALSE`. This is the recorded replay setting; the original builds' exact compiler version and runtime affinity are not stated in the source record. The original Gold1 builder used 14 OpenMP threads in its large sweeps; the pinned final builder uses 10.
- Elapsed time and peak RSS cover the builder process, including its output write. Compilation, hashing and certificate verification are separate.

A digest match identifies the historical snapshot. A mismatch cannot replay that historical receipt exactly, even when the new snapshot yields comparable bounds. To establish bounds for freshly generated bytes, use the unchanged certificate checker, for example:

```sh
NEON2_THREADS=4 bash round2/verify/neon2/run.sh gold1-check /path/to/gold1-pair
```

The checker expects both `quintet_lower.bin` and `quintet_upper.bin` in the pair directory. The rebuild places each file in its own clean build directory; link the two files into the pair directory to avoid making extra copies. Use `gold2-check` for Gold2. Pair verification has a higher memory requirement than a single builder.
